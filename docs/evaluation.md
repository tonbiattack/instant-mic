# 設計の評価と他ツールとの比較（2026-11）

このドキュメントは、instant-mic の**設計上の強み・弱みを正直に整理**し、他ツールと
比べたときに何が言えて何が言えないかを残すためのもの。

書いた時点の事実だけを書き、**測っていないことは「測っていない」と明記**する。

---

## 1. このツールの立ち位置

Android スマホを、同じ LAN の Windows PC の「音声入力キーボード」にする。

- 音声認識は OS（Google の認識サービス）に任せる
- 認識結果の解釈・補正・送信・取り消しは自分で持つ
- 音声もテキストも外部サーバーへ送らない（認識サービスを除く）

つまり **「認識エンジンを作る」のではなく「認識結果を安全に PC へ届ける」** ことに
重点を置いた作りになっている。この選択が、以下の強みと弱みの両方を決めている。

---

## 2. 強み（設計として評価できる点）

### 2.1 コマンド解釈を送信側と受信側で二重化している

スマホが「これはコマンドだ」と判断して送り、PC 側が**独立に**もう一度解釈する。
片方の判断が壊れても、危険な操作がそのまま通らない。

```
internal/speech/speech.go        … 受信側の解釈
android/.../domain/CommandParser.kt … 送信側の解釈
```

同じ規則を2箇所に保つコストは払っているが、音声コマンドは「誤爆すると文章が消える」
種類の操作なので、割に合う。

### 2.2 取り消しは「数が合わなければ消さない」

直前に入力した文字数を PC 側が記録し、要求と一致したときだけ Backspace を送る。
一致しなければ**何もせず失敗**する。曖昧なときに推測で消すと、ユーザーの文章を
壊すため。

- 記録は単回使用（`internal/server/undo.go` の `take()`）
- キー操作が挟まると記録を破棄する（カーソル位置を測れないため）
- 逐次入力では文字数を累積し、発話全体を1回で取り消せる

### 2.3 発話途中のフレーズを「絶対にコマンドにしない」フラグ

`text` メッセージの `literal: true`。受信側はコマンド解釈をせず、`コマンド` で
始まるフレーズは拒否する。これがあるので、逐次入力を入れても
「途中で『送信』と認識されて勝手に Enter」が起きない。

### 2.4 クリップボードを使わない

`SendInput` の `KEYEVENTF_UNICODE` で直接キーイベントを送る。

- IME の状態に依存せず日本語が出る
- クリップボードを汚さない（貼り付け方式でありがちな「クリップボードが上書きされる」
  「一部アプリで化ける」が起きない）

### 2.5 「疑わしければ入力しない」を一貫させている

| 場面 | 挙動 |
| --- | --- |
| 取り消しの文字数が合わない | 何も消さない |
| 逐次入力中に認識結果が修正された | 追加入力せず、確認を表示 |
| `literal` なのに `コマンド` で始まる | 入力しない |
| 危険なコマンド（設定時） | 実行前に確認 |
| 送信に失敗した | 残りを入力しない（順序が崩れるため） |

事故を避ける方向に倒す判断が全編で揃っている。**この一貫性が最も評価できる点**。

### 2.6 完全ローカル

LAN 内のみ、自己署名証明書を指紋で固定（TOFU + pinning）、トークンは
ハッシュのみ保存。音声は認識サービスに渡るが、アプリ独自のサーバーへは送らない。

---

## 3. 弱み（正直に書く）

### 3.1 認識精度は Google 頼み

こちらの成果ではない。認識サービスの変更で挙動が変わる（実測: 端末内認識は
発話中に句読点を返さず、英語を小文字 ASCII で返す）。この性質に合わせて
「無音で区切る」などの回避策を入れており、**解決ではなく回避**である。

### 3.2 性能を測っていない

「前より速く感じる」という主観はあるが、数値を取っていない。
`ACK` には `elapsedMs`（SendInput の実行時間）が入っているので測定は可能。

測るなら:

- 発話終了 → PC 入力完了までの時間（`elapsedMs` の分布）
- 送信 → ACK のラウンドトリップ
- 同じ文を10回読んだときの誤変換数
- 連続入力10発話での取りこぼし・重複数

### 3.3 Windows + Android 限定

macOS / Linux の受信側はない。`internal/input` が `SendInput` 前提。

### 3.4 ひらがなモードは回避策

漢字の選択ミスを「漢字にしない」ことで消している。読みの正確さは上がるが、
同音異義語の区別は失われる（`機構`/`器機` → `きこう`）。日本語の文章を書く用途には
向かないため、既定はオフ。

### 3.5 実機の自動テストがなかった（今回で一部解消）

単体テストは厚いが、画面と実機の回帰は手作業だった。今回 Robolectric による
Compose UI テストを追加し、確認ダイアログなど**危険な状態**は CI で検証できる
ようにした。ただしマイク・認識サービス・`SendInput` の実挙動は今も手動確認。

### 3.6 他ツールとの厳密な比較をしていない

Talon、Whisper 系、OS 標準の音声入力と横並びで測ったことはない。
「他より優れている」とは言えない。

## 4. 他ツールとの比較（言えること・言えないこと）

| 観点 | このツール | 一般に言えること |
| --- | --- | --- |
| 認識精度 | Google 依存 | 専用エンジン（Whisper 等）の方が高精度な場合がある |
| 遅延 | LAN 内で小さい（未測定） | クラウド経由より有利な設計 |
| プライバシー | 認識以外は端末内 | クラウド前提のサービスより有利 |
| 誤操作への備え | 二重解釈・確認・拒否 | ここまで徹底したものは多くない（**推測**） |
| 対応 OS | Windows + Android | 他ツールは macOS 対応が多い |
| セットアップ | QR ペアリングのみ | アカウント登録が不要な点は利点 |

**言えること**: 設計の慎重さ（2.1〜2.5）は具体的な実装として存在する。
**言えないこと**: 精度・速度で他より上とは、測っていないので言えない。

---

## 5. 次に測るなら

1. `cmd/e2eclient` で 100 回連投し、`elapsedMs` の中央値・p95 を取る
2. 同じ文を10回読んで誤変換数を数える（辞書オン/オフ、ひらがなオン/オフ）
3. 連続入力で発話が分断される回数を数える（無音判定 短め/標準/長め）
4. 送信順序の入れ替わりが 0 件であることを、逐次入力モードで確認する

## 6. 現状のテスト構成

| 層 | 内容 | 実行 |
| --- | --- | --- |
| Go 単体 | コマンド解釈、QR、ペアリング、undo、literal、送信先 | `go test ./...` |
| Kotlin 単体 | コマンド解釈、辞書、逐次送信、順序付け、危険コマンド判定 | `gradlew testDebugUnitTest` |
| Kotlin 単体（Kuromoji） | 辞書の読み取得、ひらがな変換 | 同上（JVM で動作） |

| 手動 | マイク、認識サービス、`SendInput`、ペアリング | 実機 |
